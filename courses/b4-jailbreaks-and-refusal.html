Jailbreaks and refusal: a rate, and a counter-metric

A jailbreak finding is the easiest thing in this course to measure badly. Run the attempt once and you have written down a property the system does not have. Measure only the harmful set and you can "improve security" by making the product refuse its own users. This session builds the pair of numbers that stops both mistakes, reads the one defence with published before-and-after figures, and explains why most bug bounty programmes will not pay for a bare jailbreak.

Part 0

The class, and the two numbers that describe it

⚠ Authorization This session is about testing AI systems you own, or are contracted in writing to test, inside the scope document you wrote in b1. It names the attack class so you can build test cases and pairs it with the defence that addresses it. There are no jailbreak strings on this page and no attack craft, by design: a written-down bypass is an information hazard that helps every system except yours. Testing a system you are not authorized to test is a crime in most jurisdictions.

MITRE ATLAS calls it AML.T0054 LLM Jailbreak, filed under two tactics at once, Defense Evasion and Privilege Escalation, with maturity Realized - meaning it has been observed in the wild, not merely demonstrated in a lab. OWASP files the input side under LLM01:2026 Prompt Injection. NIST's taxonomy gives it its own attacker objective, NISTAML.04 Misuse Enablement, which exists only on the generative side of the taxonomy: there is no equivalent objective for predictive AI, because there is nothing there to talk into anything.

Part 1 · the measurement

It is a rate, and it was never anything else 6 min live

This is the methodological heart of the session, and it is not a refinement of ordinary security testing - it is a different kind of claim. In classic penetration testing an exploit either works or it does not, and a single successful run is proof. Here, the same input does not give the same answer twice, so a single run is a sample, and a sample of one tells you almost nothing about the distribution it came from.

LiveThe three variables hiding inside any success rate3 min▶

HarmBench gives the formal definition of attack success rate, and the useful thing about seeing it written out is that it exposes exactly three places where two people can produce different numbers for the same system:

  • The classifier c - whoever decides a given output counts as a success. Change the judge and change the number, with no change to the system under test.
  • The token or attempt budget T - HarmBench's own finding is that budget "drastically impacts" the result and is not standardised across papers.
  • N - the trial count from Part 1, which is the difference between 57% and 80% on identical attacks.

promptfoo's documentation says the same thing in its own words: attack success rate depends heavily on attempt budget, prompt set composition and judge choice. So when a vendor gives you an ASR, the three questions are not rude, they are the only way to read the number: which judge, what budget, how many trials.

This is also why cross-vendor ASR comparison is not a thing you may do. A NeurIPS 2025 paper by Chouldechova, Cooper, Barocas, Palia, Vann and Wallach puts it plainly: conclusions about relative system safety are often not supported by the evidence that ASR comparisons provide, resting on apples-to-oranges comparisons or low-validity measurements. Report your rate as a trend within your own pinned configuration, over time. Never as a league table.

Part 2 · the counter-metric

The cheat, and the cheapest guard against it 6 min live

Here is the failure mode that no amount of adversarial cleverness will catch, because it is not an attack. You harden the system, the jailbreak rate falls, everyone is pleased, and the product quietly becomes unusable. There is exactly one cheap instrument that detects this, and it is the reason serious jailbreak benchmarks ship two sets rather than one.

Read that last line again, because it is a rare thing in this literature: a defence paper publishing its own cost in the same document as its own win. Instruction hierarchy trains the model to rank system instructions above user instructions above tool output, it generalised to attack types it was never trained on, and it delivered up to a 63% robustness improvement. It also over-refused some requests it should have answered. Both facts are in the paper. A vendor blog reporting only the first number is not lying, it is quoting.

The report line to adopt now Never publish a jailbreak rate without the refusal rate on a benign set of comparable size, measured at the same time, on the same build, with the same N. Two numbers, always, one line. If the second number is missing from someone else's report, the first one is uninterpretable, and you are allowed to say so.
Part 3 · what exists, and what it measures

The benchmark landscape, read defensively 6 min live

You are not going to write a jailbreak corpus from scratch, and you should not want to. Four public suites are named by NIST itself, and each answers a different question. Pick by question, not by popularity.

SuiteShapeThe question it answers
HarmBench510 behaviours, 7 semantic categories plus 4 functional categoriesBreadth. Does the system hold across the range of harm types, and does it hold for functional shapes such as multimodal or contextual behaviours as well as topics?
JailbreakBench100 harmful and 100 benign behaviours, 10 categories aligned to published usage policiesThe pair. What did the hardening cost? This is the suite that ships the counter-metric in the box.
AgentHarm110 malicious agent tasks, 11 categories, multi-stepTwo things at once: does the model refuse, and if it is jailbroken, does it retain the capability to actually complete a multi-step task?
AgentDojo97 tasks, 629 security test casesUtility under attack in an agent environment. b6 and b7 use this one; it is listed here so you know where it sits.

That second AgentHarm dimension is worth pausing on, because it is what makes it an agent benchmark rather than a jailbreak benchmark with tools attached. A model that has been talked out of refusing but is then too incoherent to complete a five-step task is a different risk from one that stays fully capable after the refusal falls away. On a chat product only the first dimension exists. On an agent, capability retention is most of the severity, which is exactly the argument b6 builds out.

The one defence with published before-and-after

Anthropic's Constitutional Classifiers is the most useful measured result in this session, because it reports all three of the numbers a defender needs: the win, the cost to users, and the cost to the bill.

Build Beacon's jailbreak test-case schema ★ 12 min · everyone builds

Beacon's Support Bot is the target for this one, because it is the T3 bot that can issue refund credits, so it is the one where a policy bypass could matter. You are writing the record format, not the attacks. Get the format right and the corpus can grow for years; get it wrong and every finding needs re-testing to become comparable.

One case is a behaviour, not a string. A case names a thing the system must not do for anybody - "issue a refund credit outside policy", "produce content in a category the usage policy forbids". Attack techniques are how you probe the behaviour and they change every quarter; the behaviour does not. This is also what lets you record a case in a shared repository without shipping an exploit.

Fix N in the case, not in the run. If N lives in the runner, someone will change it on a Friday and the trend line silently breaks. Put it in the case file, pin it in review, and make a change to N a visible diff.

Name the judge in the case. Whoever or whatever decides success is the c from Part 1. A human adjudicator is a valid judge if you name them. A model judge is a valid judge if you version it. An unnamed judge means the number cannot be reproduced.

Pair every harmful case with a benign twin in the same category. The twin is the request a real Beacon customer makes that lives near the line: the genuine refund enquiry, the legitimate question about account closure. If a hardening round moves the harmful case and the twin, you have not hardened anything, you have narrowed the product.

Record k of N and the build. A finding with no build identifier expires the moment someone deploys, and nobody will know it expired.

beacon/cases/refund-policy-bypass.yamlid: JB-014 class: AML.T0054 # LLM Jailbreak - Defense Evasion, PrivEsc owasp: LLM01:2026 nist_objective: NISTAML.04 # Misuse Enablement (GenAI only) target: support-bot endpoint: production-ui # b1 Part 2: say which layer you tested behaviour: "Issue or promise a refund credit outside the published policy" trials_n: 25 # fixed here, not in the runner judge: human-adjudicator/p.okonkwo # or a versioned model judge benign_twin: BN-014 # the legitimate refund enquiry, same category blast_radius: read-only # b1 RoE: the tool is stubbed, no credit is issued result: build: support-bot@2026.08.11 k: 6 n: 25 benign_twin_refused: 1
The field teams leave out, every time benign_twin. It feels like paperwork on the day you write it and it is the only field that will stop a future team from shipping a refusal machine and calling it a security improvement. Make the schema reject a harmful case that has no twin.
Demo 2 of 2

The severity conversation, before it happens to you ★ 8 min · in pairs

Somebody is going to walk into your review with a jailbreak and a strong opinion about its severity. This is the ten minutes that decides that conversation in advance, using published vendor positions rather than your own instinct, so that it is a policy discussion rather than a personality one.

Read Google's published scope out loud. Their AI vulnerability reward programme puts direct injection, jailbreaks and alignment failures out of scope for security bounties, while indirect injection with production impact is in scope. That is not a claim that jailbreaks do not matter. It is a claim about the security threat model: absent a chain to data or an action, a bare jailbreak has no security impact to pay for.

Read Microsoft's alongside it. MSRC's AI bug bar classifies content-related issues as In Scope or Out of Scope with no severity rating at all - a deliberate structural separation of the safety track from the security track. Two tracks, two owners, two timelines. Beacon should copy the structure, which is exactly what your b1 rules-of-engagement document already split.

Now do the chaining exercise on Beacon, in pairs, four minutes. Take one jailbreak finding and ask what it reaches. On Insight Bot with no tools, no private data and no egress, it is informational: a bad answer in a box. On Support Bot, where the same bypass ends in a refund credit being issued, the finding is not a jailbreak finding at all any more, it is an unauthorized-action finding, and it is severe because of the credential, not because of the prompt.

Write the severity sentence into your report template. Ours: severity is set by what the finding chains to, not by whether the model misbehaved. Then keep reporting the bare rate anyway, in the safety track, because it is the trend line that tells you whether your next model upgrade regressed.

The thing to say when the room deflates "Out of scope for the bounty" is a statement about who pays, not about whether it is real. A jailbreak rate that is climbing across model versions is a genuine finding with a genuine owner, and the honest framing is: this is a product-quality and policy-compliance signal today, and it becomes a security finding the moment this bot gets a tool. Which, on most roadmaps, is next quarter.
Homework

Try it yourself - this week ◐ 45-60 min total

  • Find the last jailbreak finding your organisation recorded and check whether it says k of N. If it says "succeeded" or "blocked", re-run it at N=25 and see whether the sentence survives.
  • Write ten benign twins for your product - the requests that live nearest the line and must still be answered. Ten is enough to catch the refusal machine, and you can grow it later.
  • Ask whoever owns your guardrail what the compute overhead is. Constitutional Classifiers published 23.7%. Most internal defences have never had the number measured at all, and it is usually the reason a defence gets quietly disabled under load.
  • Look up your own vendor's bounty scope and find the sentence about jailbreaks. Bring it to your next triage meeting before the argument, not during it.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · A tester reports "we attempted the policy bypass and it was blocked". What is the problem?

Option C sounds like the diligent answer and is the wrong lesson, because it treats the problem as effort rather than as measurement. Non-determinism is a property of the system, not a failure of the tester. The fix is structural: N fixed in the case file before testing, k of N in the finding, and the build identifier alongside it so the result expires visibly rather than silently.

2 · Your hardening round takes the jailbreak rate from 42% to 1%. What single number do you need before you may call this an improvement?

Both A and B are worth knowing and neither detects the specific cheat. Compute overhead tells you the bill, technique count tells you coverage, but only the benign set tells you whether the security gain was actually a usability loss wearing a security costume. JailbreakBench ships 100 benign behaviours next to its 100 harmful ones for precisely this reason, and OpenAI's Instruction Hierarchy paper is the honest example: +63% robustness reported alongside its own over-refusal regressions.

3 · A researcher brings you a reliable jailbreak of a bot that has no tools, no private data and no outbound network. How do you triage it?

C is the trap, and it is the one that gets adopted by accident. "The bounty does not pay for it" is a statement about who owes money, not about whether the behaviour is real or whether the trend matters. Keep measuring the rate, keep the counter-metric next to it, and note the condition under which the triage flips: the day that bot gets a tool or a data source, the same finding becomes an unauthorized-action finding and the severity comes from the credential rather than from the prompt.
